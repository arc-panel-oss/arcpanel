# E34 REST API v2, batch 1 — design

**Status:** Approved, in progress (2026-10-07, see §13) · **Epic:** E34 (new: REST API v2) · **Base design:** [02 Laravel foundation](../../design/02-laravel-foundation.md) §4.3, [03 Tenancy](../../design/03-tenancy-and-authorization.md) §7–§8, [01 Architecture](../../design/01-architecture-overview.md) §4.3 · **Previous spec:** [E29 OpenAPI document of API v1](./2026-10-07-001-e29-openapi-design.md) · **Roadmap:** new epic E34

## 1. Summary

API v1 (`POST /api/`, `lib/api/index.php`) runs any `v-*` command by name with positional arguments. It is complete but hard to use, and it scopes non-admin keys only by comparing one argument. This spec adds **API v2**: resource routes under `/api/v2/` in the Laravel panel app, with named JSON fields, HTTP verbs and status codes, owner scoping through the panel's policies, and an OpenAPI document generated from the code.

Batch 1 delivers the foundation and three resources: users, packages and web domains (with aliases, SSL and Let's Encrypt). Later batches add DNS, mail, databases, cron and backups, one spec each. API v1 stays unchanged and supported.

v2 is the base of three clients built outside this repository by the maintainer (§11): a TypeScript SDK, the `arc` command line tool with AWS-style profiles, and skills that let AI agents operate a panel. Decisions D9–D14 exist for them.

## 2. Decisions taken in the brainstorm

| #   | Question                   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Where v2 lives             | **Laravel panel app**, `routes/api.php` with the prefix `api/v2` and a stateless middleware group (no session, no cookies, no CSRF). `arcpanel-nginx` gets a `location ^~ /api/v2/` block to `web-app/public/index.php`; the longest prefix wins, so `/api/` stays with v1.                                                                                                                                                                                                                  |
| D2  | Code shape                 | **API controllers of their own** in `App\Http\Controllers\Api\V2`, thin as AGENTS.md §6 asks: FormRequest → policy → service → API Resource. Planning code that lives in a web controller today moves into an action class used by both the web and the API controller; no logic is written twice.                                                                                                                                                                                           |
| D3  | Authentication             | **The existing access keys**, sent as `Authorization: Bearer ACCESS_KEY:SECRET_KEY`. A new command `v-check-access-key-permissions` checks the key and returns its user and the commands it may run. The secret goes to it through a `Secret` temp file, never on the command line. No new token store: the panel has no database yet (E15).                                                                                                                                                 |
| D4  | Principal of a key         | The **owner of the key**, with the role and read-only state of that user and no impersonation. Policies, `OwnerScope` and `TenancyDirectory` apply exactly as for that user signed in: outside the tree **404**, refused inside it **403**, read-only principals **403** on writes.                                                                                                                                                                                                          |
| D5  | Permission sets            | A key with permission sets may only run their commands. Read endpoints declare the commands they run; write endpoints check every command of their plan (the `Step` list) **before the first one runs**, so a refused call changes nothing. The commands depend on the role (a reseller creates users with `v-add-reseller-user`), which is why plans are checked rather than routes.                                                                                                        |
| D6  | Sets for v2                | Non-admin keys need permission sets (`is_key_permissions_format_valid`). A broad set would also open those commands to v1, whose only check is the user argument (a user key could change its own package). So v2 ships **v2-only sets** marked `API='v2'`: `v2-read` (the list commands of v2) and `v2-write` (every command of v2). `get_apis_commands`, which v1 uses, skips sets marked `API='v2'`; the new command reads them. The roles are enforced by the policies, not by the sets. |
| D7  | Roles                      | **Admin, reseller and user** from batch 1, each with the endpoints its role has in the panel (§6).                                                                                                                                                                                                                                                                                                                                                                                           |
| D8  | API switches               | `API_SYSTEM` (`0` off, `1` admin keys only, `2` every key) and `API_ALLOWED_IP` apply to v2 as to v1.                                                                                                                                                                                                                                                                                                                                                                                        |
| D9  | Wire format                | JSON bodies and responses, **snake_case** keys (`disk_used`, not `U_DISK`), named fields instead of positions. One object as `{"data": {…}}`, a list as `{"data": […], "meta": {}}`; `meta` is reserved so that pagination can be added later without breaking clients. No pagination in batch 1.                                                                                                                                                                                            |
| D10 | Errors                     | `{"error": {"code": "E_EXISTS", "message": "…", "fields": {…}}}` with the command error names of `ExitCode` and the statuses of `ExitCode::httpStatus()` (404, 409, 422, 429, 503, 500). API-layer codes: `E_UNAUTHENTICATED` 401, `E_API_DISABLED` 403, `E_FORBIDDEN` 403, `E_NOTEXIST` 404, `E_VALIDATION` 422 (with `fields`), `E_RATE_LIMIT` 429 (with `Retry-After`). The codes are an enum in the OpenAPI document.                                                                    |
| D11 | Dry run                    | Every write endpoint accepts `?dry_run=1`: the request is validated, authorized and checked against the permission sets, and the answer lists the planned steps (`label`, `command`, arguments with secrets masked) without running any. AI agents and `arc` use it to show a plan and ask before they act.                                                                                                                                                                                  |
| D12 | Who am I                   | `GET /api/v2/me` returns the key id, user, role, read-only state, permission sets and allowed commands (`*` when unrestricted), and the panel and API versions. `arc configure` and the agent skills use it to check a profile.                                                                                                                                                                                                                                                              |
| D13 | Headers                    | Every response carries `ArcPanel-Version` (panel version) and `X-Request-Id` (the client's value or a new one, also written to the log line of the call). `429` carries `Retry-After`. `202` carries `Location` of the resource to poll.                                                                                                                                                                                                                                                     |
| D14 | OpenAPI and stability      | **Scramble** (`dedoc/scramble` 0.13, MIT, supports Laravel 13) generates OpenAPI 3.1 from the routes, FormRequests and Resources; `php artisan scramble:export` writes `docs/api/v2/openapi.json`, which CI checks. Every operation has an explicit, stable `operationId` in camelCase (`listUsers`, `createUser`, `changeUserPackage`), which the SDK turns into method names. No documentation route in the app. Within v2 only additive changes are allowed; a breaking change is v3.     |
| D15 | Long operations            | Let's Encrypt is queued as the panel queues it today and answers **202** with `Location` of the domain; its SSL status shows the progress. A general task endpoint comes with backups in a later batch.                                                                                                                                                                                                                                                                                      |
| D16 | Rate limit and brute force | 60 requests per minute per key (Laravel's limiter on the file cache), and 10 failed authentications per minute per IP. Failures go to `auth.log` like v1, so fail2ban rules keep working.                                                                                                                                                                                                                                                                                                    |
| D17 | Retries                    | Resources are created under a name the client picks (user name, package name, domain), so a repeated create answers `409 E_EXISTS` instead of creating a duplicate. No `Idempotency-Key` header in batch 1.                                                                                                                                                                                                                                                                                  |

## 4. Authentication and authorization

### 4.1 `v-check-access-key-permissions`

```text
# info: check an access key for API v2
# options: ACCESS_KEY_ID SECRET_FILE IP [FORMAT]
```

- Reads the secret from `SECRET_FILE` (a `Secret` temp file of the panel), then runs the checks of `v-check-access-key` through the same functions: the key exists, the secret matches, the owner exists and is not suspended.
- Prints `USER`, `PERMISSIONS` (the set names) and `COMMANDS` (the expanded commands, `*` when the key is the admin's and has no sets). Expands sets marked `API='v2'` as well as the others.
- Logs like `v-check-access-key`: a success to the user history (category `API`), a failure to `$ARCPANEL/log/auth.log`. Exit codes: `E_PASSWORD` for a wrong key or secret, `E_SUSPENDED`, `E_FORBIDDEN`.
- Added to the panel's allow-list (`config/arc-commands.php` is generated from `bin/`).

### 4.2 v2-only permission sets

- `install/common/api/v2-read` and `install/common/api/v2-write`: `ROLE='user'`, `API='v2'`, `COMMANDS='…'`. The command lists are generated from the commands that the v2 endpoints declare or plan, and a Pest test fails when a v2 endpoint runs a command missing from `v2-write`, or a read endpoint runs one missing from `v2-read`.
- `get_apis_commands` (`func/main.sh`) skips a set whose file has `API='v2'`, so v1 never runs those commands for such a key. The access key page of the panel lists both sets with a short explanation.

### 4.3 Request pipeline

1. `ApiEnabled`: `API_SYSTEM` and `API_ALLOWED_IP` (D8), else `403 E_API_DISABLED`.
2. `AuthenticateAccessKey`: parses the header, runs `v-check-access-key-permissions`, binds the `Principal` (D4) and the `KeyPermissions` (allowed commands); `401 E_UNAUTHENTICATED` otherwise, counted by the failure limiter (D16).
3. `throttle:api-v2` (D16), then the existing `not-readonly` and `effective-user` middleware where the route needs them.
4. Controller: FormRequest, policy, service. `PlanRunner` asks `KeyPermissions` to approve the whole plan before the first step, and returns the plan unrun when `dry_run` is set (D11). Read endpoints check their declared commands the same way.
5. Exception handler: `ArcCommandException`, validation, authorization and HTTP exceptions become the error body of D10 for every `api/v2/*` request.

`Principal` gets one optional field, the access key id, used by the log lines; the session-based resolver does not change.

## 5. Wire format

- Field names follow the panel's records (`UserRecord`, `PackageRecord`, the web domain records) in snake_case, through one API Resource per resource. Values keep their types: numbers as numbers, `yes`/`no` as booleans, comma lists as arrays, unlimited quotas as `null`.
- Requests use the same names. `PATCH` changes only the fields it sends. Passwords are accepted on write and never returned.
- Dates are ISO 8601 in the server's time zone.
- Every enum (roles, shells, backend templates, SSL states) appears as an enum in the OpenAPI document, so the SDK gets union types.

## 7. OpenAPI document

- `dedoc/scramble` goes in `require-dev`: the export runs in CI and on the workstation only, so the packaged panel never loads it. Its documentation routes are switched off.
- Controllers carry the `operationId` (Scramble's attribute or PHPDoc tag) and Resources declare their field types so the inferred schemas are exact. Shared components: `Error`, `ErrorCode`, `DryRun`, `Me`.
- `docs/api/v2/openapi.json` is committed. A CI job (`.github/workflows/lint.yml`, PHP 8.5, `composer install`) runs the export and fails when the file differs.
- The security scheme is HTTP bearer, so generated clients send the header themselves.

## 8. Testing

- **BATS** (`test/arcpanel-api-v2.bats`): `v-check-access-key-permissions` (valid key, wrong secret, suspended owner, expanded sets, `*` for the admin); `get_apis_commands` skips `API='v2'` sets, so v1 refuses a v2 command for such a key.
- **Pest feature** per endpoint, through the real middleware with `ArcCommandFake`: admin, reseller A, reseller B and user against a fixture with two trees (200/403/404 per the matrix), cross-tenant 404, read-only 403, `401` without or with a wrong key, `E_API_DISABLED` for each `API_SYSTEM` value, rate limit with `Retry-After`, dry run that runs nothing, a permission set that refuses a plan and runs nothing, error bodies of D10.
- **Pest unit:** the Resources (types, booleans, `null` quotas, no password field), `KeyPermissions`, the error mapping, the `v2-read` / `v2-write` lists against the declared and planned commands.
- **Smoke** (`test/arcpanel-api-v2-smoke.sh`, root on the test server, throw-away users `arcsmoke*`): creates a key, then with curl a user, a package and a web domain, a dry run, a refused call, and deletes them.

## 11. Clients built on v2

The maintainer builds three clients in their own repositories; they are not part of this spec, but v2 is designed for them:

| Client                      | What it needs from v2                                                                                                                                                 |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `arcpanel-sdk` (TypeScript) | A typed OpenAPI 3.1 document with stable `operationId`s, enums and one error schema (D9, D10, D14); `docs/api/v2/openapi.json` is its input                           |
| `arcpanel-cli` (`arc`)      | One header per server, so AWS-style profiles (endpoint, key, secret, CA bundle for self-signed panels) need nothing from the server; `GET /me` checks a profile (D12) |
| `arcpanel-agent-skills`     | Dry run before every change (D11), machine-readable errors (D10), read-only keys through `v2-read` (D6), `Retry-After` and `Location` (D13)                           |

Commands that v2 does not cover yet stay reachable through v1 with the same access key; a client may offer that as a fallback.

## 12. Risks

| Risk                                                       | Mitigation                                                                                                                     |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| A v2 set leaks commands to v1                              | `get_apis_commands` skips `API='v2'` sets; BATS proves v1 refuses them                                                         |
| One sudo call per request for authentication (about 50 ms) | Accepted; no cache, because a cache would hold secrets                                                                         |
| A plan fails half-way although the permission check passed | The same rule as the panel: `PlanRunner` stops at the first failure and reports the steps that ran                             |
| Scramble infers a wrong schema                             | Resources declare their types; Pest unit tests check the Resources; the exported document is reviewed in each milestone's diff |
| `setup-php` has no PHP 8.5 build in CI                     | Fall back to the test server for the export check and record it in the implementation notes                                    |
| A web controller and its API twin drift apart              | The planning code moves into shared action classes (D2); the web Pest tests keep passing                                       |

## 13. Implementation notes

The work log of each milestone: what was built, where it differs from the sections above, and what was verified. Where this section and the sections above differ, this section wins.

### M1 Foundation (2026-10-07)

**Built.**

- `bin/v-check-access-key-permissions ACCESS_KEY_ID SECRET_FILE IP [FORMAT]` (§4.1). It also prints `ROLE` (from the owner's `user.conf`), so the panel needs no `v-list-user` per request. `COMMANDS` is a list in both formats; an administrator's key without sets prints the list `["*"]`. The secret file must be a regular file under `/tmp/` without `..`, the rule of `is_password_valid`. Exit codes: `E_PASSWORD` for every failure except `E_SUSPENDED` (owner suspended) and `E_FORBIDEN` (a non-admin key without sets). It does not check demo mode: it changes nothing but the logs.
- `get_apis_commands PERMISSIONS [v1|v2]` (`func/main.sh`): skips the sets marked for v2 unless asked for `v2`; it resets `COMMANDS` before each set, so a set without the key no longer inherits the previous one's. `v-list-api` and `v-list-apis` print the new key (`API_VERSION`, `1` when absent; shell listing column `VERSION`).
- `install/common/api/v2-read` and `v2-write` (`ROLE='user'`), installed by the installer (`cp -rf install/common/api`) and refreshed by `v-add-sys-arcpanel` on every install and upgrade, because their lists follow the panel app. In M1 they hold `v-list-sys-config`; each milestone adds the commands of its endpoints.
- `src/deb/nginx/nginx.conf`: `location ^~ /api/v2/` to `web-app/public/index.php`; `/api/` stays with `lib/api/index.php`.
- Panel app, namespace `App\Api`: `KeyPermissions` (the key as the command describes it), `KeyScopedArcCommand` (refuses a command outside the sets before it runs), `PlanGate` (checks a whole plan and the commands an endpoint runs after it before the first step, answers the dry run, turns a failed step into the error body), `ErrorCode`, `ApiException`, `ErrorRenderer`, `ApiHeaders`. Middleware `App\Http\Middleware\Api\{StartApiRequest, ApiEnabled, AuthenticateAccessKey}` and the `api-v2` rate limiter (`AppServiceProvider`). `GET /me` (`MeController`, `MeResource`, enum `ApiRole`). `Principal` has the optional `accessKey`.
- The access key page shows a hint under `v2-read` and `v2-write`.
- OpenAPI: `dedoc/scramble` 0.13.47 in `require-dev`, excluded from package discovery and registered on the console only by `ApiDocsServiceProvider`, without its documentation routes. `php artisan arcpanel:api-docs [--check]` writes `docs/api/v2/openapi.json`. CI job `openapi-v2` (`.github/workflows/lint.yml`, `shivammathur/setup-php` with PHP 8.5) runs the check.

**Differences from the sections above.**

- **The marker of the v2 sets is `API_VERSION='2'`, not `API='v2'` (D6).** `source_conf` assigns with `declare -g`, so a set file with `API=` would overwrite the `API` key of `arcpanel.conf` (the switch of the legacy API) in every command that reads sets.
- **The plan check and the dry run are in `PlanGate`, not in `PlanRunner` (§4.3 step 4).** The web pages keep their runners unchanged; API controllers pass their plan and their runner (`UserService::apply`, `WebDomainService::apply`) to `PlanGate::execute()`. `KeyScopedArcCommand` adds the guard for everything else an endpoint runs (reads, counters, clean-ups), so a command missing from a set is refused even where no plan names it.
- **The routes are registered in the `then:` callback of `bootstrap/app.php`, not with `withRouting(api:)`.** The `api` group brings `SubstituteBindings`, and Laravel's middleware priority would then move `throttle:api-v2` in front of `AuthenticateAccessKey`, before the key is known. API v2 has no model bindings.
- **Error codes (D10):** `E_METHOD_NOT_ALLOWED` (405) and `E_SERVER` (500, a command that could not run or an unexpected error) were added; exit code 10 (`E_FORBIDEN` in `func/main.sh`) is spelled `E_FORBIDDEN`, like the API-layer code.
- **Document (§7):** Scramble's own `scramble:export` is not used. `arcpanel:api-docs` runs Scramble's generator and completes the document with what the code cannot tell: servers (`https://{host}:{port}/api/v2`), the bearer scheme, the `Error`, `ErrorCode`, `PlanStep` and `DryRun` schemas, the error responses of every operation, the `dry_run` parameter and its `200` answer (`oneOf` with the resource where the operation answers `200`), and the `X-Request-Id`, `ArcPanel-Version` and `Location` headers. Schemas of Resources lose the `Resource` suffix (`Me`, not `MeResource`). It fails when an operation has no `@operationId`, a duplicate or one that is not camelCase. Tags come from the `@tags` line of the controller. The file is in `.prettierignore`: it is generated, with PHP's JSON layout.
- **Switches take up to 60 s:** `API_SYSTEM` and `API_ALLOWED_IP` are read through `SysConfig`, cached for 60 s like every key of `arcpanel.conf` (design 02).

**Verified.**

- BATS `test/arcpanel-api-v2.bats` on `arcpanel-test`: 13 of 13 (sets installed and marked, every set command exists, `v2-read` is part of `v2-write`, `get_apis_commands` skips v2 sets, the four answers of the check, the secret file rule, suspended owner, API v1 refuses a v2 command and still runs the commands of the other sets of a key). `test/arcpanel-panel-app.bats` 26 of 26 after the change of `v-add-sys-arcpanel`.
- Pest: `tests/Feature/ApiV2FoundationTest.php` and `tests/Unit/ApiV2Test.php` (35 tests), and the whole suite, 863 passed. The test helpers `apiKey()` and `apiAs()` give non-admin keys the commands of the shipped set files, so a later endpoint that runs a command missing from its set fails its tests.
- Through nginx on `arcpanel-test`: `GET /api/v2/me` answers `200` with an administrator's key once `API_ALLOWED_IP` allows the address (`403 E_API_DISABLED` before, with `X-Request-Id` and `ArcPanel-Version`); `POST /api/` still reaches API v1.
- `arcpanel:api-docs` and `--check` on `arcpanel-test`; the CI job itself runs on the next push. Pint, shellcheck (severity error), Prettier and the brand check are clean.

### M2 Users (2026-10-07)

**Built.**

- `App\Http\Controllers\Api\V2\UserController` with the ten operations of §6.1, the requests `App\Http\Requests\Api\V2\{StoreUserRequest, UpdateUserRequest, UserPackageRequest, UserPasswordRequest}` (base `ApiRequest`) and `UserResource` (schema `User`: typed limits with `null` for unlimited, usage, `created_at` as server-local `YYYY-MM-DDTHH:MM:SS`, no password and no reset key).
- Shared actions (D2): `App\Services\Users\UserActions` holds the choice checks and plans that `UserController::store` and `UserEditController::general` and `package` of the web pages had (taken username, package, owner, reseller quota and `USERS`, language), plus `deleteRefusal()` and `ownerOptions()`. The web controllers call it; their tests pass unchanged. `UserService::apply()` now keeps the exit code of a failed step, so the API answers with its status.
- The v2 sets list the commands of these endpoints; `v-check-reseller-quota` is in `v2-read` (it changes nothing).
- `test/arcpanel-api-v2-smoke.sh`: the foundation checks and the user life cycle through nginx and curl (§8); later milestones extend it.
- Fix of M1: `StartApiRequest` drops the key, the principal, the key-scoped `ArcCommand` and the scoped instances of an earlier request. PHP-FPM starts every request afresh, but an application that serves several requests (the test suite) kept the first key.

**Differences from the sections above.**

- **`PATCH /users/{user}` follows `UserPolicy::update()`:** a user may change the name, e-mail and language of its own account, as on its "My account" page (D7); §6.1 named administrators and resellers only. The password has its own operation (`PUT …/password`, `204`).
- **A repeated create answers `409 E_EXISTS` before any check** (D17); a taken name found by the choice checks of the web page stays a validation error there.
- **Suspend and unsuspend are idempotent:** a user already in the asked state answers `200` and runs no command, so a retry does not fail with `E_SUSPENDED`.
- **Language of a new user:** the server language when the request leaves it out; a language the server does not have is now refused on the web page too.
- **Success statuses in the document:** Scramble does not follow `setStatusCode(201)` or `noContent()` after the early dry-run return, so a controller method declares its success status with an `@status` tag, which `arcpanel:api-docs` reads from the route's method.

### M3 Packages (2026-10-07)

**Built.**

- `App\Http\Controllers\Api\V2\PackageController` with the six operations of §6.2; requests `StorePackageRequest` and `UpdatePackageRequest` (base `PackageRequest`) and `CopyPackageRequest`; `PackageResource` (schema `Package`).
- Wire format of a package: `templates` (`web`, `backend`, `proxy`, `dns`), `limits` (the counted keys with `null` for unlimited, plus `rate_limit` and `backups`), `resources` (cgroup limits), `shell`, `nameservers` (a list), `backups_incremental`, `reseller` (`users`, `packages`, `visible`), `ports`, `node` and `docker`. `name` is the stored name used in paths (`hostco_gold`), `label` the name its owner sees (`gold`), `owner` the reseller that made it.
- Shared actions (D2): `App\Services\Packages\PackageActions` holds what `PackageController` of the web pages checked and planned (visible packages, taken names, templates and shells of the server, two name servers, a reseller's own limits for counted keys, ports, Node.js and Docker). It takes the values as package-file keys, so the web form and the API body only differ in how they build them. The form defaults moved to `PackageService::defaults()`.
- The v2 sets list the package commands; the template and shell lists are in `v2-write` (only writes check them).

**Differences from the sections above.**

- **Every field of a create may be left out:** it takes the value of the add form, with the name servers of the `default` package. `PATCH` keeps the fields it was not sent; the package is applied to its users as on the web page.
- **Errors use the API field names:** the checks of `PackageActions` name the fields of the web form (`disk_quota`, `web_template`), and `PackageRequest::withApiFields()` renames them (`limits.disk_mb`, `templates.web`).
- **Status codes:** a taken name answers `409 E_EXISTS` (create and copy), a package with users `409 E_INUSE`; `default` cannot be deleted (`403`), as on the web page. A user's key answers `403` on every package operation.
